## 〇、一句话结论

**分行**：现在存的是「一条一行」的编辑惯例，不是原刻本真实的逐行换行；「自然段」现在就能做，
对目录体（六藝略类）几乎零成本（CSS 开关），对语录/纪传体（论语类）需要真的合并段落边界，
但仍是纯机械操作。**真正的「原书排版还原」（逐列换行对照页面图像）现在的数据做不到**，
要等 CV 行框数据。

**字形**：繁（现状）／简（OpenCC）**两种已经在线上跑着**（book-index-manager 0.9.x，`opencc-js`
的 `t2cn` 转换器）——用户以为要新做的「繁简切换」其实是现状。「异体字／原书字形」现在做不到，
现有的两处近似数据都对不上号：维基 `variants` 是**异文**（不同版本的字句差异），不是**异体字**
（同一个字的不同写法）；CV 字形库确实是异体字的候选数据源，但还没有链路把它接到 book-text。

**底层格式**：`guji-markdown` 有自己的网页渲染器（`@open-guji/markdown-web`），**竖排是纯 CSS**
（`guji-vertical.css`，`writing-mode: vertical-rl`），本道已用真实数据渲染出来（样张 04/05）——
够「网页阅读＋竖排」用，但版心／鱼尾／印章／夹注双栏精确断行这类**版式还原**它不做（设计上就没打算做，
样张 04/05 的夹注双栏是纯 CSS column，肉眼能看出不如活字精细）。真正的版式还原是 `luatex-cn`
（LaTeX 宏包，产 PDF）与它的纯 JS 移植 `webtex-cn`（本道已用同一批数据实测渲染出四库全书仿真页面，
样张 06）。**两条链路目前互不相通**：`book-text` 存的 `.md` 与 `webtex-cn` 吃的 `.tex` 语法不同，
没有转换器，本道是**手工**把 `<…>` 夹注改写成 `\夹注{…}` 才跑通样张 06 的。

**切换**：现状**没有任何切换 UI**——网站目前只有一份固定渲染（繁体、条目分行、guji-markdown 系
横排）。四个维度（分行×字形×底层格式）理论上可以正交组合，但**没必要都做成用户开关**：
字形（繁/简）适合做用户级开关（已有先例）；分行（分行/自然段）适合做用户级开关；
底层格式（guji-markdown 网页版 vs webtex-cn 仿真版）**更像是场景选择**（阅读用前者，
"查看原版式"／打印用后者），不是随手切的开关，建议按 Work/Book 有没有配齐数据来决定"能不能提供
第二种查看方式"的按钮，而不是四个维度全乘出 N 个开关塞进同一个工具条。

## 二、五问逐条

### 1. 分行

**现状**：

- 「一条一行」是**当前存储的编辑惯例**（F-MD-06「忠实底本层一条一行」），**不等于原刻本的真实换行**——
  原刻本是竖排、每列若干字，现在的「一行」对应的是一个书目条目/一句话，不是一列。
- 真正「按古籍原来的分行方式」需要**行级坐标**（这一行在原书哪一列、多少字）。现有数据里：
  - CV 线（open-guji-cv，本道未读，按任务书交底）产物有行框，但还没有交付进 book-text（M3 交底：
    「CV 交付进 book-text 推后，等 CV 有一册完整、置信度足够高的文本」）；
  - 影印本 OCR 整理本**只有页码**（`<!-- pN -->`），没有行号——降级到「按页」已是现有数据能给的上限；
  - 维基文库全文（論語、公羊傳样张）**完全没有**页码或行号，是纯文本转录，降级到「无版面对应，只有段落」。
- 「自然段」现状**完全没有**——线上只有一种断行方式（上面 `pre-line` 那条）。

**实测发现（決定选项难度的关键点）**：两种体裁的底层数据形状不同，导致「做自然段」的成本天差地别：

| 体裁 | 存储形状 | 「自然段」怎么做 | 成本 |
|---|---|---|---|
| 目录体（六藝略类） | 条目间只有 `\n`，无空行 | **纯 CSS**：把 `white-space: pre-line` 换成 `normal`，浏览器自动把 `\n` 折叠成空格——**不用碰内容** | 几乎零成本，样张 01 已验证 |
| 语录/经传体（論語、公羊傳类） | 条目间是空行（天然 Markdown 段落，即 CommonMark 里各自一个 `<p>`） | 现状每条已经是独立块；「自然段」要把同一章/年内的多条**真的拼进一个 `<p>`**（`.join('　')` 之类），是内容层操作，虽然仍是机械拼接不涉及理解 | 比目录体贵，但仍无需人工判断 |

**选项**：

- A. 只做「条目分行」（现状），不做自然段——最省事，但不解决用户提的问题。
- B. 「自然段」做成**纯前端显示层**转换（不改存储）：目录体走 CSS 开关；语录体走一个通用小函数
  （按同一标题/章节层级把连续条目拼接），**两套体裁各写一条规则**，规则数量可控（现在只有这两种体裁，
   F-MD-06/08 已经在区分"忠实底本层"与"结构化产物"两条线，天然对应）。
- C. 「原书排版换行」（真正对照原书页面/列）——**现在不做**，等 CV 行框数据接进来；接进来之后，
  这一档展示实质上是"把 CV 的行框坐标当成一种展示模式"，不是 book-text 现有体裁能派生的。

**推荐**：B，且明确把 C 排进"等数据"档，不与 B 混着做——用户说的"两种"多半是 B 的两态
（现状条目分行 vs 聚合自然段），C（对照真实版面）是另一件事，值得单独立一条待办而不是塞进 M3 范围。

**代价**：B 对目录体几乎零成本；对语录体要写一个"按结构层级聚合"的小函数（纯前端，不改
book-text 存储），估计半天工作量；C 无法估价，依赖 CV 交付时间表。

### 2. 字形三模式

**现状**（见上「一句话结论」与「当前线上」）：

- **繁体**：存储原样，现状即此，零成本。
- **简体**：`opencc-js`（`t2cn`：繁转简，含大陆规范字表）**已经在生产环境跑着**，本道用同一个包
  在样张里复现（`node_modules/opencc-js`，转换结果见样张 01/02/03 简体列），专名与古字有没有误转——
  本道抽查样张三部**未见误转**（人名「施、孟、梁丘」「服氏」等专名转换正常，因为这些字本身
  繁简同形或转换表已覆盖），但**没有做过全库扫描**，误转是个存量风险而非本道能穷举的问题，
  建议按网站总管现有的分级/校验机制（如有）持续抽查，不因为样张没抽到就当作零风险。
- **异体字／原书字形**：**没有可用数据**。核实两个候选数据源都对不上：
  - 維基全文的 `variants` 字段（見樣張 02 對應 `full_text/wikisource-01/index.json`）是**异文**——
    记录的是"这句话不同版本怎么写"（如「也已」vs「也已矣」），是**词句级差异**，不是"同一个字换个写法"；
  - CV 字形库（open-guji-cv 线，本道未读代码，按任务书与既有交底转述）是字形匹配用的模板库，
    **理论上**是异体字数据的候选来源，但现在**没有链路**把它接到 book-text 的展示层——
    它服务的是 CV 自己的定字流程，不是给网站生成"这个字还有几种写法可切换"的数据。
  - `guji-markdown` spec 本身**没有异体字记号**（本道查过 `spec/syntax.md` 全文，只有校勘三式
    改/删/补，没有"同字异形"这一类）。

**选项**：

- A. 现在只做繁／简两态，异体字列为"待数据"，不强行拿异文凑数。
- B. 把维基 `variants`（异文）包装成一个"查看其他版本读法"的功能，**挂靠"字形三模式"名下**——
  但这样命名会混淆"版本异文"与"字形异体"两个不同概念，不推荐直接算作用户要的第三态。
- C. 单独给"版本异文"做一个展示位（不算字形模式，算校勘/版本信息的一部分），与字形三模式脱钩。

**推荐**：A + C——异体字模式明确排到"等 CV 字形库数据打通"之后；`variants` 异文单独做展示
（不算字形第三态，按其本来的语义处理，即校勘/版本信息），避免命名混淆导致以后维护者看错数据语义。

**代价**：A 零成本（现状已具备）；异体字要做，前提是先有"字→异体字集合"的查得到的数据表，
这不是前端能生造的，属于另一条待办（CV 字形库导出接口），不在本方案能定成本的范围内。

### 3. guji-markdown 与 luatex-cn／webtex-cn 的分工

**现状（本道实测，非转述）**：

| | `guji-markdown` (`@open-guji/markdown-web`) | `luatex-cn` | `webtex-cn` |
|---|---|---|---|
| 输入 | `.gmd`／兼容 `book-text` 现有 `.md`（`<…>` 夹注、`《…》` 书名号已能直接解析，本道用未改动的 六藝略.md／公羊傳.md 片段直接跑通，样张 04/05） | `.tex`（LuaTeX 宏包，`\documentclass{ltc-guji}`） | 与 `luatex-cn` **兼容的 `.tex` 子集**（纯 JS 重实现，不需要装 LaTeX） |
| 运行环境 | 浏览器／Node，零外部依赖 | 需要本机/服务器装 TeX Live + LuaTeX，编译产出 PDF | 浏览器／Node，零依赖（本道直接 `import` 源码跑通，见样张 06） |
| 竖排能力 | **CSS 竖排**（`writing-mode: vertical-rl`），夹注双栏靠 CSS `column`，本道实测（样张 04/05）**能看，但版式精细度有限**（双栏断行是 CSS 自动分栏，非逐字精算） | **版式引擎**：版心、鱼尾、双行小注自动平衡断行、印章、句读三态、乌丝栏——本道未跑（需要 LaTeX 环境，本道只读不装工具链，按 README 走查代码与既有截图核实功能存在），效果见仓库自带截图（四库全书文渊阁本、红楼梦甲戌本） | **同一版式引擎的 JS 重实现**，本道**实测能在 Node 里直接产出完整仿真页面**（样张 06：漢志六藝略易類，四库全书彩色模板，含版心／鱼尾／夹注双栏），不需要装 LaTeX |
| 与 book-text 的转换器 | **有**（book-text 的 `.md` 基本就是 guji-markdown 兼容格式，T5 已把 `<…>` 定为正规记法） | 无 | **无**——本道跑样张 06 时是**手工**把 `<…>` 逐条改写成 `\夹注{…}` 才能喂给它，没有自动转换脚本 |

**结论**：`guji-markdown` 本身就有网页渲染器，不需要"和 luatex-cn 分工"意义上的接力——它是
"日常网页阅读＋轻竖排"的默认层，一路可用（书名号／夹注／校勘三式，横竖排都有 CSS）。
`luatex-cn`／`webtex-cn` 服务的是"版式精确还原"（仿真古籍页面／可打印 PDF）这个**不同的场景**，
不是"guji-markdown 排不好时的下一级"。真正缺的是**`.md`（guji-markdown 兼容）→ `.tex`
（luatex-cn/webtex-cn 兼容）转换器**——现在完全没有，本道是手工改的。

**选项**：

- A. 网页阅读（含轻竖排）**默认用 guji-markdown-web**，不建自动转换器，"仿真版式"场景
  （若要做，如"查看原版式"按钮／导出 PDF）**先手工/半自动转換**个别样书试点，量大了再决定
  是否值得写自动转换器。
- B. 现在就写 `.md → .tex` 自动转换器，两条链路打通，所有书都能一键切「仿真版式」视图。
- C. 放弃 `webtex-cn`／`luatex-cn` 这条线，竖排只做 guji-markdown 的 CSS 版本，版式还原
  留给"以后有人要印纸书再说"。

**推荐**：A——两边现在都还没经过"多本书批量跑通"的验证（本道只跑通 1 部书的 1 段），
写自动转换器之前应该先看清楚 `.md` 里还有多少 guji-markdown 没覆盖但 luatex-cn 有专门命令的
古籍元素（抬头、乌丝栏、印章位置……这些多数是版式层的东西，book-text 存储里本来就没有，
转换器也生不出来）——**这条转换器的可行边界比想象的窄**：能转的只是「夹注、书名号、校勘」这几个
guji-markdown 已有对应指令的元素，版心／印章／句读体例这些是**排版参数**，不在 `.md` 里，
天然不该指望"转换器"生成，得由渲染时按模板配置（如 `luatex-cn` 的"模板系统"）。

**代价**：A 几乎零成本（现状已经是这样）；B 的成本被低估的地方在"覆盖率"——如果只覆盖夹注/书名号/
校勘三式，转出来的是"骨架对但版式参数靠模板猜"的仿真页，用户如果想要的是"这本书原刻本什么样"，
转换器给不了（那是版式还原，不是内容转换）。

### 4. 切换

**现状**：**无任何切换 UI**。网站现在是「繁体＋条目分行＋guji-markdown 横排」这一份固定渲染
（本道读 `book-index-manager` 代码得出，未读 `kaiyuanguji-web` 前端页面代码——UI 入口的实现
归网站总管，本道只确认了数据渲染逻辑层面「有没有可切的状态」，答案是有一处（`locale`，字形），
没暴露成明显开关的可能性存在，需网站总管确认）。

**选项**（分维度，不是"要不要做一个总开关"）：

| 维度 | 建议做成用户开关？ | 理由 |
|---|---|---|
| 字形（繁/简） | **是**，已有实现，只差确认 UI 入口位置 | 转换器现成、无成本、用户随时可能想切 |
| 分行（条目/自然段） | **是** | 一旦 §二·1 的 B 案落地，两态都是纯前端渲染，切换成本低 |
| 底层格式（guji-markdown/webtex-cn 仿真版） | **否，做成场景入口而非随手开关** | 仿真版依赖手工/半自动转换（§二·3），不是每部书都有；做成"若这部书有仿真版数据，显示一个『查看原版式』按钮"，而不是塞进同一个开关条，避免用户点了却发现这本书没有 |
| 异体字 | 暂不涉及（无数据） | 见 §二·2 |

**"哪些书能切"的判据**：

- 字形／分行：**所有** `collated_edition`／`full_text` 都能切（纯前端渲染，不依赖额外数据）。
- 仿真版式：只有**经过手工/半自动转换、生成了对应 `.tex` 或渲染产物**的书才能切，需要一个
  「本书是否有仿真版」的标记（可以是文件存在性检查，不必新增字段）。

**维基版与自校版的切换**（用户特别提到的过渡期需求）：

- 现状 book-text 的 `full_text/<key>/` 目录设计（[11-全文搜集落点](../进度/E-文本整理本/11-全文搜集落点.md)）
  本来就是**多 `<key>` 并存**（如未来 `wikisource-01` 与自校 `self-01` 同目录下不同 key），
  `text_quality.grade` 字段（source／rough／fine…）已经是"哪个更可信"的现成刻度。
- 展示上的选项：
  - A. 默认显示 `grade` 最高的一份，用户可切到其他 `<key>`（下拉或标签），**每个 `<key>`
    自己的字形/分行状态独立记忆**。
  - B. 只显示最高 `grade` 的一份，其他 `<key>` 只在"查看版本历史"里能看到，不做主视图切换。
- **推荐 A**——这正是长期方向（自校逐步替代维基）里用户需要"看得到差异、能对比"的场景，
  技术上多 `<key>` 已经是现成数据结构，不需要新设计。

**默认值建议**：字形默认繁体（存储原样，最贴近原文，且现状默认也是这个）；分行默认「条目分行」
（现状即此，改默认值是易变更的产品决策，不属于本道要定的事，只给保守建议：先不改默认，
观察用户反馈再动）。

### 5. 对规范 v1 的要求

**结论：目前不需要新增或修改 T5 规范 v1 的任何字段。** 逐条对照：

| 展示模式需要的东西 | T5 规范 v1 现状 | 是否够用 |
|---|---|---|
| 分行（自然段聚合） | 存储不变，聚合是前端渲染层的事 | 够，不需要新字段 |
| 字形（简体） | 存储不变，OpenCC 实时转换 | 够 |
| 字形（异体字） | 无字段，且**不该现在加**——加了字段也填不进数据（没有数据源） | 不加；等 CV 字形库有导出接口后再评估要不要给 book-text 加一个引用字段 |
| 底层格式转换（`.md`→`.tex`） | F-MD-01 已把 `<…>` 定为夹注正规记法，转换器靠这个记法就能抓夹注；书名号 `《…》` 本来就是纯文本，两边都认 | 够，转换器要解决的是"луatex-cn 命令覆盖面"问题，不是"book-text 缺字段" |
| 维基/自校多版本切换 | `full_text/<key>/` 多目录并存 + `text_quality.grade` 已经是现成机制（[11-全文搜集落点](../进度/E-文本整理本/11-全文搜集落点.md)） | 够 |
| 页码/行号（供"原书排版换行"） | 现状：`<!-- pN -->` 有页无行；CV 行框数据未接入 | **不够，但不是本方案要解决的**——等 CV 数据接入时，落点与字段怎么设计是那时候的事，不必现在为了"以防以后要用"预留字段（预留了也不知道形状对不对） |

**唯一值得记一笔、但不算"要求"的观察**：F-MD-06/08（一条一行 vs 结构化产物两种体裁并存、
标题层级映射留给 M3）在本方案里被直接用上了（§二·1 的两套"自然段"成本判断），
说明 T5 那两条"留给 M3 再定"的项，**M3（本方案）已经隐含把判断做完了**——不需要再回 T5 补规则，
两条 T5 原文保持"不写死全局映射"的克制是对的，展示层的判断放展示层就够。

   现在不为它预留字段？

   要不要现在投入写 `.md→.tex` 自动转换器，还是先手工转几本试点观察需求再定？
