## 〇、一句话结论

CV 线现有产物（Step1 borders、Step2 column_windows、Step3 cells、Step4 char_index、
Step7 seed_admit）已经覆盖本草案要的绝大部分字段——本草案做的事主要是**把分散在
五个 Step 产物里的字段，按"书→册→页→版框→列→格→字"这条链重新分层、落成一份
可持久化的存储格式**，而不是发明新的几何算法或识别逻辑。唯一**真正缺**的是：
① 印章（CV 无对应产物）；② 现代印刷链的原图坐标回映射（`to_original()` 尚未实现，
只影响横排现代印刷链，不影响本草案主要针对的刻本竖排链）；③ 校勘/异文与本格式的
挂接方式（本版本只留字段位，不设计具体 schema）。三条都写进 §七 待定问题清单。

## 一、层级

```
书（book-index Book/Work id）
└ 册／卷（CV workspace 的 book，如 vol01；与古籍目录「卷」不一定一一对应，见下）
  └ 页（page，1 起）
    └ 版框（border，Step1 产物，一页一份，含界行）
      └ 列（column，右→左从 1 起；版心/页边等非正文列见 §三）
        └ 格（cell/slot，列内逻辑位置：正文 1..n，抬头格 -n_raised..-1，跳过 0）
          └ 字（一格通常一字；夹注 a/b 各自一串字，单行小注占格但不成对）
```

**"册"与"卷"不是同一个概念，草案在这里不强行对齐**：CV workspace 的 `book`
是"跑一次管线的单元"（如 `books/vol01.yaml`），可能对应古籍目录里的一卷、几卷，
或一册的一部分，视原书实际装订与扫描切分而定（如四库总目卷首单独一个 `vol01`）。
本草案的"册/卷"层字段只记 `cv_book`（跑批单元 id）与可选的 `juan_range`
（该跑批单元覆盖的卷次，人工填，不由 CV 推导），不试图从 CV 数据反推真实卷次边界。

### 坐标系（CV 回单第 1 点提醒的三处已逐项核实）

CV 现有两套规范空间（`open_guji_cv/core/spec.py:20-22`）：

| 空间 | 定义 | 用在哪 |
|---|---|---|
| `raw_page_px@top-right`（`RAW_TR`） | **原图规范空间**：右上原点，x 向左递增，y 向下递增（`core/anchor.py:3-4`，用户 2026-09-03 裁「古籍从右上角起」） | `borders`（Step1，`kinds/borders.py:147`）、`char_index.bbox_page`（Step4，`kinds/chars.py:76`）、`cells.CellRec.quad_page`（Step3，`kinds/cells.py:32-33`） |
| `raw_page_px@top-left`（`RAW_TL`） | OpenCV / 旧 v1 产物，标准左上原点（`core/spec.py:21`） | 老数据、`glyph_store` 实例（本道样例实测，见样例 README） |
| `column_px`（`COLUMN_PX`） | Step2 矫正后的单列图坐标，随列而异，非页面全局坐标 | `cells`（Step3，`kinds/cells.py:101-103`）、`char_index`（Step4，`kinds/chars.py:74-75`）、`glyph_match`/`ocr_candidates` 等（`kinds/recog.py:245-254`） |

**本草案统一到 `raw_page_px@top-right`**（下称 RAW_TR）作为每字 `bbox` 的存储空间，理由：
它是页面全局坐标（不随列变化，可直接叠图）、是 CV 现行（非旧版）规范、且 Step1
版框、Step3 `quad_page`都已经是这个空间，三层几何量统一坐标系才能互相核验。

**换算**：`RAW_TL → RAW_TR` 用 `core/anchor.py:20-32` 的 `bbox_tl_to_tr(bbox, width)`：
只翻转 x（`x_tr = (width-1) - x_tl`），y 不变；`width` 取该页原图实测像素宽。
`COLUMN_PX → RAW_TR` **不是本草案自己实现**，直接读已有的 `CharRec.bbox_page`
（Step4 算好的"同一框回到原图、换到规范空间"外接框，`kinds/chars.py:1-4`）或
`CellRec.quad_page`（Step3，逆映射回原图的四角，`kinds/cells.py:32-33`）取外接框，
**两者都可能为空**（老产物、或没有做过列→页逆映射），此时 `bbox` 记 `null`，
`bbox_source` 字段如实记来源（`bbox_page`／`quad_page`／`none`），不允许为了"总有值"
去拿列坐标充数——列坐标不能直接当页坐标用，会指向错误位置。

**已知缺口（CV 回单第 1 点，本道核实结果）**：`raw_page_px` 这个"规范空间"对**现代
印刷链的横排书**而言，实际是"读序空间"，即原图被顺时针旋转 90° 之后的坐标
（`open_guji_cv/core/step.py:161-174`）："产物坐标从此是读序空间，不是原图坐标……
面向人的三处（控制台叠图、金标锚点、Step9 导出）要转回去，走 `core/anchor.py` 的
`to_original()`；那部分**尚未实现**"。这意味着：**若一本书走的是现代印刷链
（横排原书），本草案的 `bbox` 暂时不能保证叠回真实原始扫描图**——只有刻本竖排链
（本草案的主要场景）不受影响。已列入 §七·1。

## 二、每字字段

一个字位（对应 CV 的一个"格"，`id = book:page:col:slot[sub]`，沿用 CV 全流程通用主键，
`open_guji_cv/report/slots.py:97`「`id` 是全管线通用主键……深链、金标、事件、比对报告都用它对齐」）：

| 字段 | 类型 | 含义 | 数据源（文件:行号） |
|---|---|---|---|
| `id` | string | 字位主键 `book:page:col:slot[a\|b]` | `report/slots.py:94-97` |
| `glyph_id` | string\|null | 刻例 id（字形库检索键）。**本草案裁定与 `id` 同构**——CV 现状本来就是同一套主键（`instances.instance_id` 沿用 `CharRec.id` 同一格式，`clustering/align_gold.py:119`），不新造第二套编号 | `products/kinds/chars.py:38-39` |
| `char` | string\|null | 字形，**照录刻本字形**；`null`＝阙文（见 `unreadable`）。2026-09-26 起全流程只存字形，不存"读法"（`recog.py:188-189`；`render/guji_markdown.py:130-132`） | `products/kinds/recog.py::AdmitRec.char` |
| `page` | int | 页号（1 起） | `core/spec.py:163-164` |
| `col` | int | 列号，右→左从 1 起 | `products/kinds/cells.py::ColumnCells.col` |
| `slot` | int | 列内逻辑位置：正文 1..n，抬头格 -n_raised..-1，跳 0 | `products/kinds/cells.py:5-6` |
| `sub` | "a"\|"b"\|null | 双行夹注左右子列；单行小注 `sub=null` 但 `kind="jiazhu_solo"` 与正文区分 | `report/slots.py:31-33` |
| `order` | int | 列内阅读顺序（**已排好序，直接用，不要重新算**——权威实现 `utils/jiazhu_order.py::sort_by_reading()`） | `products/kinds/cells.py::CellRec.order`；01-结果排版.md §一末「读序不要自己重新算」 |
| `kind` | enum | `char`\|`blank`\|`jiazhu_a`\|`jiazhu_b`\|`jiazhu_solo`\|`punct`（现代链） | `products/kinds/cells.py:25` |
| `bbox` | [x0,y0,x1,y1]\|null | 原图坐标，RAW_TR（见 §一坐标系） | 优先 `chars.py::CharRec.bbox_page`，退化 `cells.py::CellRec.quad_page` 外接框 |
| `bbox_source` | "bbox_page"\|"quad_page"\|"none" | `bbox` 实际取自哪一层，`bbox=null` 时必须是 `"none"`，不可空缺 | 本草案新定 |
| `channel` | string\|null | 放行通道（`match_solo`／`context`／…），**与 `human_reviewed` 分开记，不合成置信数**（CV 回单第 2 点提醒） | `products/kinds/recog.py::AdmitRec.channel` |
| `human_reviewed` | bool | 是否人工裁过（`channel=="human"`） | `report/slots.py::SlotRec.human` |
| `excluded` | bool | 排除名单·非字（墨污/切坏图块，本不是字，不占字数） | `report/slots.py:22-23` |
| `defect` | bool | 排除名单·切坏/残（**字确实在这儿**，只是图块不能进库，占位出阙文） | `report/slots.py:24`，`recog.py` `evidence.excluded` 理由 `seg_defect`/`damaged` |
| `unreadable` | bool | 阙文：`admit=False and char is None and not excluded` | `report/slots.py:25`；`render/guji_markdown.py:38-41` |
| `guess` | string\|null | `defect`（damaged）格人给的"最像哪个字"，渲染成 `□{guess=X}` | `recog.py` `evidence.guess`；`render/guji_markdown.py:136-141` |
| `variant_note` | string\|null（可选） | 异文/校记挂点，**本版本只留字段位，不设计具体校勘 schema**（见 §六、§七·5） | 本草案新定 |

**三种"没有字"的格必须分开，不能合并**（`report/slots.py:18-29` 的三分表，本草案原样采纳）：

| | `kind` | 有 `AdmitRec`？ | 含义 | 本草案字段组合 |
|---|---|---|---|---|
| 版式留白 | `blank` | 没有 | 抬头前空格、列末空格 | `kind="blank"`，其余标记全 false/null |
| 排除·非字 | `char` | 有，理由 `not_a_char` | 墨污/切坏，根本不是字 | `excluded=true` |
| 排除·残缺 | `char` | 有，理由 `seg_defect`/`damaged` | 字确实在，图块不能进库 | `defect=true`（占位出阙文） |
| 阙文 | `char` | 有，`admit=False and char is None` | 确实是字但认不出 | `unreadable=true` |

`channel`／`human_reviewed` 不用 CV 回单说的"置信数"是因为 CV 现状本身就没有概率式
置信度（`AdmitRec` 只有 `admit`/`channel`/`provenance`，见 CV 总管回单
`inbox/总管-文本/20260926-0845-note-CV总管-自校文本格式数据源.md`「有来源，没有概率式
置信度」），格式层没有可合成的东西，忠实转发比编一个假分数更可靠。

## 四、派生

### ①横排分段 guji-markdown（无损，因为本格式字段已完全覆盖现有渲染算法用到的量）

现有 `open_guji_cv/render/guji_markdown.py::render_column`（`guji_markdown.py:56-123`）
join Step3 `cells` + Step7 `seed_admit` 现算的量——`kind`/`char`/`order`/`sub`/
`n_raised`/`lead_blank`/`excluded`/`defect`/`guess`/`unreadable`——本草案字段设计
（§二、§三）**逐一对应**，即本格式相当于把现算的 `SlotRec` 流**持久化落盘**，
派生算法可以原样搬（本道样例 `自校格式样例/scripts/export_demo.py` 已实测跑通，
产出 `p0010.export.md`，含正文、抬头 `^`、双行夹注 `<a|b>`、阙文 `[[]]`、空白跳过
五种分支，见样例 README）。**不是本草案重新设计一套导出算法**——现有算法直接可用，
只是输入源从"现算 join"变成"读持久化格式"。

### ②luatex-cn／webtex-cn 版式还原

需要三层几何数据：版框（版心、鱼尾定位）、列窗口（`border_top_in_column` 等，
决定列内文字带范围）、格几何（`bbox`/`quad_page`，决定逐字精确定位）——本草案
在"版框"层与"列"层都保留了这些量（§三"界行"一行；列层建议同时留一份
`ColumnWindowRec` 精简摘录：`border_top_in_column`/`border_bottom_in_column`/
`band`，见 `products/kinds/columns.py:41-64`，本版本暂只点名字段来源，不逐项定死，
留给样式还原真正动手时按需取）。**转换器本身不在本草案范围**——[展示格式方案
§二·3](2026-09-展示格式方案.md) 已确认 `.md→.tex` 转换器"先手工试点，不急着写通用
转换器"，本草案只保证"数据齐"，不实现转换。

### 丢了什么／能否回映射

横排分段 md 导出会丢弃 `bbox`/`slot`/`col` 等几何信息（导出的是纯文本）。
**推荐做法**：不在 md 正文里插锚点弄脏文本（会跟 guji-markdown 现有记号冲突、
维基文库导出也不认），而是**md 与本格式 JSON 并存**，靠"md 是从 JSON 按 `order`
顺序拼出来的"这个派生关系本身做回映射——即，md 里第 k 个非空白/非排除字符，
对应 JSON 数组里按 `order` 排序后跳过 `blank`/`excluded` 的第 k 条记录。
这个映射关系不需要另外发一套协议，只要求**派生时保留导出用的过滤/排序规则**
（本草案 §四·①已给出，与现有 `render_column` 完全一致）不擅自改动。

## 五、落点

**新增 `Book/<c1>/<c2>/<c3>/<book_id>/layout/`**，与 [E-11](../进度/E-文本整理本/11-全文搜集落点.md)
定的 `full_text/` **并列而不是并入**——理由：`full_text/` 是"给读者看的文本"资产
（E-11：网站"全文" tab 直接读它），本格式是"字级坐标的结构化数据"，目的与消费者都不同
（前者可以从后者派生，混进 `full_text/` 会让文本 tab 的渲染逻辑多处理一堆它不需要的几何字段）。

```
Book/<c1>/<c2>/<c3>/<book_id>/layout/
├── index.json          册/卷级元信息：对应哪个 CV workspace book、产物指纹、格式版本号
└── pNNNN.json          单页数据，字段=本草案 §二、§三
```

**按页存，不是整册一个大 JSON**：① [展示格式方案](2026-09-展示格式方案.md) 已确认
"原书排版还原"要等这套数据，交互层大概率是"翻某一页看版式"，按页存贴近读取模式；
② 体量控制——本道样例页（约 20 字位，只含 §三 部分示例）JSON 约 2.5 KB；
按实测密度（`chars_per_line: 21`／`expected_cols: 9`，`guji-workspace` 私有仓
`96mid1ogzk-…/books/vol01.yaml`，一页约 9×21≈189 字位上限，含标点/空白/夹注实际
略少）粗估单页 JSON 数万字节到十余万字节量级，一册（如四库总目单个 `vol01` 约
数十至二百余页）大致数 MB 到十余 MB 量级——按页存便于局部更新、局部读取，
不必每次改动重写整册文件。此估算未取得真实 Step3/Step7 产物核实字位密度
（见样例 README 的数据缺口说明），**只是量级判断，不是精确数字**，列入 §七·7。

`index.json` 建议字段：`schema`（`guji-layout/v1`）、`cv_book`（跑批单元 id）、
`fingerprint`（产物指纹，供判断是否过期重导）、`revision`。

## 六、与现有规范的关系

- **guji-markdown**：现在只是"展示层记法"，本身不含坐标（`spec/syntax.md` 全篇
  未见坐标字段，本道查过全文，只有校勘三式改/删/补，没有"同字异形"/坐标类记号）。
  本格式是"数据层"，guji-markdown 由本格式**派生**（见 §四·①），关系是
  下游消费者，不是平级或竞争关系。
- **[book-text 格式规范 v1](2026-09-book-text格式规范.md)**：管的是
  `collated_edition`／`full_text`／`fragments`／`sources` 四类既有资产，编号规则
  `F-<资产简称>-NN`。本格式是**第五类新资产**，建议编号简称 `LY`（layout），
  纳入同一编号规则下（如未来 `F-LY-01` 记 `layout/index.json` 必现字段），
  **本草案不越权直接改 v1 文档**，只在 §七·6 向文本总管提议由 T5 校验器的维护者
  评估是否要加 `F-LY-*` 系列规则。
- **[展示格式方案](2026-09-展示格式方案.md)**：该方案 §六·2（用户定案）正是本草案的
  委托来源——"原书分行、竖排版式还原、图文对照、异体字（原书字形）都建立在这套格式之上"。
  本草案 §三"版心"/"界行"、§四·②的几何字段留白，都是为该方案点名的四项能力
