## 〇、一句话结论

**129 个表格章现存的线性化文本，本身已经把「哪些行是表头」「哪些格是空的」
「哪些格是合并的」三样结构信息丢了**——不是「格式不够正式」这么简单，是**内容已经
不完整**：全库机械抽样（见 §一·3）显示，只从现存 `<!-- table -->` 文本出发做转换，
**55,580 个数据格里有 41,154 个（74.0%）列数对不齐**，必须靠补占位符兜底，且补的
位置不一定对——因为这些「消失的格子」在现有存储里已经无迹可寻，唯一能坐实的办法
是回到维基原始 wikitext 重新解析（§四）。

**推荐记法**：guji-markdown 自定义容器块 `:::table`（与既有 `:::tt` 容器同构），
配合「表头行用 `!` 前缀、数据行必须写满与表头相同的列数、空格用显式 `_` 占位、
跨列用 `{n}` 后缀、跨行用 `^n` 起格＋`^` 续格」的行内小语法——本质上还是今天这套
「一行一格」的书写习惯，只是把「省略＝没有」改成「省略是错误，空必须显式」，
并把表头行、合并格都标出来。不选 GFM 管道表（连 rowspan/colspan 这个概念都没有），
不选裸 HTML `<table>`（会掉进 guji-markdown「原始 HTML 默认不解析」的坑，见 §二·2）。
**理由与三方对照见 §二。**

**真合并格不是罕见情况**：本道后来把 §一·2 的判断从"6 个样例抽查"扩到**全量
129 章重抓**（§四实测过程中顺手做的，见 §一·3），结果是**24/129 章（18.6%）
真的有 colspan 或 rowspan**，且个别章很密集（明史/卷109 单章 154 处
rowspan）。**方案定稿版已经把 `^` 续行标记设计进去并在 6 个样例里验证过**
（遼史/卷66 是真合并格样例，见 §三）——本文档更早的一版曾判断"数据行没见过
真 rowspan，先不设计"，那是只抽查 6 个样例得出的错误结论，**已被全量重抓推翻，
不要沿用**。

**转换器**：`古籍文本/scripts/table_convert.py`，联网重抓维基原始 wikitext/HTML 后
按真实结构解析（表头、colspan、rowspan、显式空格）转换——这条路径在 6 个样例上
全部验证通过（§三）。同时提供不联网的机械兜底模式，把「回不来的信息」计数上报，
不假装能复原。

**合并格信息怎么补回来**：129 章规模小，直接用现成的 `wiki_api.get_revision()`
（`scripts/fetch-book-fulltext/`，自带 3 秒节流与磁盘缓存）逐页重抓即可，
**不需要搭维基 dump 环境**——本道实测这条 API 路径在本会话云端环境里就能跑通
（见 §四）。

### 2. 任务书要求的 5 类形态：实测结果与两处改判

任务书原定 5 类（纯矩阵／有合并格／表中带夹注／表头多层／空格排的表）。
本道先按**能从现存线性化文本机械判断的信号**分了一版，随后用 6 个样例回到
原始 wikitext 逐一核对，又把核对范围**扩到全部 129 章**（§一·3／§四，反正
重抓一遍也要做），拿到两处站得住脚的改判：

- **"有合并格"与"空格排的表"这两类，绝大多数是同一个成因**——不是维基原表
  真的用了 rowspan/colspan 或刻意排版留空，而是**我们自己的转换管线把源文
  显式的空单元格（含 wikitext 里明写的全角空格「　」占位）当成了"这一格不
  存在"给删掉了**（根因见下）。
- 但**"合并格"本身不是稀有情况**：全量重抓后有 **24/129 章（18.6%）真的存在
  colspan 或 rowspan**（§一·3 表），不能因为最初 6 个样例只抽到 1 个真
  colspan（漢書/卷013，且只在表头行）就判定"数据行没有真合并格、可以不做"——
  这是本道中途自我纠正的一处判断，写在这里是为了让下一道看到"6 个样例的
  归纳有多容易带偏"这件事本身。

**根因**（`scripts/fetch-book-fulltext/guji_clean.py` `_split_table_row`）：

```python
cells.extend(_strip_cell_attr(p).strip() for p in parts)
...
cells = [c for c in cells if c != '']
```

`.strip()` 对 Unicode 空白一视同仁，全角空格 U+3000 和普通空格一样被吃掉；
吃成空串之后又被 `if c != ''` 整格删除。**源文一个显式的"这格没有"，
到我们的线性化文本里变成"这一格从物理上消失了"**，后面的格全部错位一位。
`_strip_cell_attr` 同时把 `colspan="…"`／`rowspan="…"` 这些属性文本整段丢弃，
真合并格信息也没了。

**实测对照**（6 个样例，见 §三 与展示样张）：

| 样例 | 现存线性化文本 | 原始 wikitext 真实情况 |
|---|---|---|
| 宋史/卷210 宰輔年表 | 多行列数不齐（如「961」行只有 3 格，表头 6 格） | 源文写的是 `\|960\|\|...\|\| ... \|\| \|` 六个 `\|\|`，其中三个显式为空——**不是合并，是空**；表头用 `!`/`!!`，与数据行的区分现在没有留痕 |
| 漢書/卷013 異姓諸侯王表 | 行长从 3 格到 18 格不等 | **真有** colspan：两行表头，`楚` `colspan=4`、`趙` `colspan=2` 等；夹注是 `{{*|…}}` 模板（现有管线已经会转成 `<…>`，这条链路本身没问题）；正文里大量「　」占位被吃 |
| 新唐書/卷073上 宰相世系表 | 每行长度不一 | **12 列固定**的稀疏矩阵，几乎全用「　」占位，**无 colspan/rowspan**——列数"不齐"完全是我们自己吃空格造成的假象 |
| 元史/卷096 食貨志官俸表 | 部分行整体错位（内容对不上应有的语义列） | 3 列固定，某些行首格为空，我们的管线把首格吃掉后**后面的内容全部串到前一列去了** |
| 新五代史/卷60 職方考 | 列数基本整齐（这份碰巧没怎么触发问题） | wikitext 用"每格独占一行"写法（不是同行 `\|\|`），本例源文本身没有空格，管线也没出错——**不是所有表都受影响，受不受影响取决于源文有没有显式空格** |
| 遼史/卷42 曆象志損益表 | 3 列，本例列数碰巧整齐 | 裸 HTML `<table><th>`/`<td>`写法，规范嵌套，无 colspan/rowspan——现有管线对这类"干净"HTML 表格处理没问题 |

**改判**：把任务书的 5 类合并为 3 个更贴合实测的维度（并非互斥，一章可能同时占几条）：

| 维度 | 判据（可从现存文本机械算） | 章数（分母 129） |
|---|---|---|
| **含夹注** | 表格块内出现 `<…>` | **41 章** |
| **列数与表头不一致**（下称"错位"） | 表内至少一行的格数 ≠ 首行格数，超过 15% 的行 | **114 章**（§ 3 有全量补齐比例） |
| **真合并格（colspan/rowspan）** | 需要回到 wikitext 才能确认；**全量重抓 129 章后实测：24 章（18.6%）真的有** | **24 章**（§一·3 全量重抓数字，见下） |
| **表头行有显式标记**（wikitext 用 `!`/`!!`） | 现存线性化文本已丢失这个区分 | **43 章**（33.3%）源文本来就有 `!` 表头行；其余 86 章源文本身就没有单独的表头行（数据表直接开始），不是"丢了"，是"本来没有" |
| **裸 HTML `<table>` 写法**（非 wikitext `{|...|}`） | 两种源写法都要能解析（§三 6 个样例覆盖了两种） | **34 章**（26.4%） |

「错位」114 章里，41 章同时命中"含夹注"（一份表格既有夹注又有空格丢失）。
真正三类都不占（既无夹注、列数又整齐）的只有 **15 章**——这 15 章即便原样保留

金史／元史体量较小的表）。

**没有找到独立的"纯粹空格排"类**——空格排的表在源头就是"稀疏矩阵 + 全角空格
占位"，跟"错位"是同一个技术根因，不必另立一类。但**"多层表头"确实是独立
存在的一类**，且往往和真合并格同时出现（漢書/卷013 是"两行 `!` 表头 + 表头行
colspan"；遼史/卷66 是"数据行大量 rowspan/colspan"，见 §一·3 全量扫描按部拆分）：

|---|---|---|

### 3. 全量量化：现存文本能不能机械修复？

用 `table_convert.py from-stored`（不联网，只吃现存 `<!-- table -->` 文本，
按首行列数在行尾补 `_` 占位）跑全部 129 章、624 个表：

| 指标 | 数值 |
|---|---|
| 数据行总数 | 55,580 行 |
| 需要补齐的行数 | **41,154 行（74.0%）** |
| 按部拆分 | 宋史 26,777/32,466（82.5%）、新唐書 7,944/12,404（64.0%）、明史 2,732/4,061（67.3%）、漢書 1,595/1,770（90.1%）、史記 1,109/1,591（69.7%）、其余部＜5% |

**结论**：机械补齐能保证"列数对得上"，但**补的位置是猜的**——从 §一·2 的实测看，
"某行只有 3 格、表头有 6 格"，真实空格可能在第 2、3 格，也可能在第 4、5、6 格，
现存文本已经无法区分。这不是"格式选哪种记法"能解决的问题，是**这批数据需要
一次性回源重取**（§四）。转换器的 `from-stored` 模式因此**不建议用于正式入库**，
只用于"没法联网时占位、且必须把补了多少处如实计入 `ai_note`"的降级场景。

## 二、方案：三种记法对照

### 候选一：GFM 管道表（`\| a \| b \|` + `---` 分隔行）

```markdown
| 公元 | 紀年 | 宰相進拜加官 |
| --- | --- | --- |
| 960 | 建隆元年 | ... |
```

- **合并格**：GFM 规范里**根本没有 colspan/rowspan 的概念**——管道表的数据模型
  就是矩形网格，没有"跨格"这回事。唯一的workaround 是内容重复或留空+人工注记，
  没法忠实表达漢書/卷013 那种两行表头＋colspan。
- **夹注**：单元格内容里的 `<…>`／guji-markdown 其他记号照常生效（管道表只是
  行级结构，行内解析不变），但**单元格内容不能跨行、不能包含裸 `|`**（需转义
  `\|`），公羊傳类"傳文即长夹注"的表格（如果一格里要放几百字案语）很别扭。
- **网站要改多少**：`kaiyuanguji-web` 的 `MarkdownRenderer.tsx`（`react-markdown`
  + `remark-gfm`）**已经能渲染出带样式的表格**（`table`/`th`/`td` 组件已写好，
  见 `nextjs/src/components/markdown/MarkdownRenderer.tsx`）——但这条渲染链路
  现在只用于站内说明页（`extraction`/`roadmap` 等静态文档），**不是**
  `book-index-ui`（`book-index-manager/ui`）渲染 `collated_edition` 正文用的那套。
  正文渲染现状是 `CollatedEdition.tsx` + `primitives.tsx` 里一个**手写的正则扫描器**
  （`scanJiazhu`/`renderInterlinear`），完全不过 remark／mdast，本来就不认识
  任何表格记法，选哪种都要**新写**表格渲染代码，GFM 在这条渲染链路上**没有
  "网站已经会渲染"这个优势**，那只是另一条完全不相关的渲染路径的既有能力。
- **与自校格式怎么接**：自校文本（每字带坐标）大概率不会走"remark 解析 markdown
  表格"这条路，GFM 在这一点上不占优势也不吃亏（三种候选都一样，见 §五）。

### 候选二：HTML `<table>` 子集（原样保留维基 HTML 结构）

```markdown
<table><tr><th colspan="4">楚</th></tr>
<tr><td rowspan="2">960</td>...</tr></table>
```

- **合并格**：原生表达，`colspan`/`rowspan` 属性直接照抄，是三个候选里**唯一
  不需要发明新语法就能表达合并格**的。
- **致命问题**：guji-markdown spec 明确写死**「古籍文本默认不允许原始 HTML」**
  （`spec/ast.md` §2.5：`allowDangerousHtml: false`，源文中的 HTML 块在
  mdast → hast 阶段被**丢弃**）。更麻烦的是 spec §0.1.4 把「原始 HTML 标签」列为
  **不生效区**——也就是说，如果表格用 `<table>` 包起来，**表格内部的夹注 `<…>`
  会被当成"在 HTML 标签内"而按字面输出，不会被解析成夹注**！这是本方案排除
  HTML 候选的核心原因：不是"网站要多做点工作"，是**和 book-text 现有的行内标记
  体系直接冲突**，除非渲染器专门为"表格内部再单独走一次 guji-markdown 解析"
  开个特例（可以做，但等于把 HTML 表格又拆开重新解析一遍，那不如一开始就不用
  HTML）。此外维基原始 HTML 表格本身就不总是良构——T9 报告记过晉書/宋書等六部
  的裸 HTML 表格 `<td>` 常不闭合，需要专门的容错解析，手写/校对时也比 directive
  语法更容易出错（多一个闭合标签就坏）。
- **网站要改多少**：需要显式打开 `allowDangerousHtml`（如果未来真的接上
  guji-markdown-web 渲染），且必须为"表格内部重新跑一遍夹注解析"写专门代码；
  `book-index-ui` 现在的手写渲染器如果要支持这个记法，等于要写一个小型 HTML
  解析器，比支持 `:::table` 容器块更重。

### 候选三（推荐）：guji-markdown 自定义容器块 `:::table`

`guji-markdown` 的整个扩展体系已经是**generic directives**（`micromark-extension-directive`
+ `mdast-util-directive`），`:::tt{n=2}` 这种容器块**已经是现成的、经过验证的
写法**（`spec/syntax.md` §6，多行抬头用的就是这个）。表格照抄同一个模式：

```markdown
:::table
!公元 | 紀年 | 宰相進拜加官{2} | 罷免
960 | 建隆元年庚申太祖正月甲辰即位 | 二月乙亥，... | _
961 | 二年辛酉 | 范質　王溥　魏仁浦 | _
:::
```

**具体约定**（本道的最小设计，供文本总管定案，不是 guji-markdown 已注册的正式
指令——注册需要改 `spec/directives.md`／`packages/core/src/directives.ts`／
`packages/web/src/handlers.ts`，那是 guji-markdown 仓自己的事，本道只读）：

| 要素 | 写法 | 对应 §一 发现的哪个问题 |
|---|---|---|
| 表头行 | 行首加一个 `!` | 恢复"哪几行是表头"这个当前完全丢失的区分 |
| 数据行必须写满 | 每行格数 = 表头格数，一个不能少 | 修复"空单元格被静默删除"这个影响 74% 行的 bug |
| 显式空格 | 单元格写 `_` | 同上，让"这格没有"变成看得见、能统计的记号，而不是"格子物理消失" |
| 跨列（colspan） | 单元格内容后缀 `{n}`，如 `楚{4}` | 表达真合并格（漢書/卷013 那种），且和现有 `:tt{n=1}` 的属性写法同构，不引入新符号系统 |
| 跨行（rowspan） | 起格写 `内容{n}^r`（`{n}` 是可选的 colspan，`^r` 是 rowspan 数）；它续占的下几行在对应列位置写一个光秃秃的 `^`（续格标记，取自账簿"仝上"的传统写法），使每一行的格数仍然等于表头总列数——**已实现并在遼史/卷66（真实 rowspan/colspan 密集样本）验证过**，见 §三 | 修复"数据行合并格丢失"，全量重抓证实这不是罕见情况（24/129 章，§一·2） |
| 单元格内嵌行内记号 | 原样嵌套，`<…>`／`《…》`／`/…/` 照常解析——因为整体仍在 directive／markdown 解析范围内，**不落入不生效区** | HTML 候选的致命伤，这里天然没有 |
| 夹注 | 单元格内容里直接写 `<…>`（本来就是 guji-markdown 正规记法，T5 已定） | 和 candidate 一/二 相同，不是本候选独有优势，但至少不倒退 |

**为什么不怕"发明了新语法"**：`{n}` 后缀在 spec 里已经有先例（`:tt{n=1}`／
`:kg{n=2}` 的属性写法），`_` 占位符是本方案唯一真正新加的记号——而且它解决的
恰恰是本次画像发现的最大问题（74% 行数据丢失位置信息）。三个候选里，只有这个
候选能同时做到「表达合并格」「不破坏已有行内标记」「复用已验证的 directive
解析器」。

**网站要改多少**：无论选哪个候选，**`book-index-ui` 现在都不认识任何表格记法**
（§二·候选一 已说明现状是手写正则扫描器，不过 remark）。真正的改动量落在：

1. **解析层**（新增，三候选都要写，工作量相近）：在 `collated_edition` 的
   md→json 转换步骤里新增"识别 `:::table` 块，解析成结构化行列数据"的代码——
   这一步应该发生在**入库时**（沿用 book-text 现有"md 为真源、json 为解析产物"
   两层架构，见 [规划/文本.md](../../../team/文本/目标.md) 中期原则 3），
   而不是让浏览器端在渲染时现解析表格文本。也就是说 `section.json` 应该多一种
   `type: "table"`，直接带 `rows: [{cells: [{text, colspan, rowspan}]}]}`
   这样的结构化数据。
2. **渲染层**（新增，三候选都要写）：`book-index-ui` 加一个 `<GujiTable>`
   React 组件，吃上面那个结构化 JSON，输出真 `<table><th>/<td rowspan=.. colspan=..>`——
   不需要在浏览器里解析 markdown 表格语法，直接按结构渲染，跟选哪种存储记法
   **无关**（三候选殊途同归到同一个结构化 JSON，渲染层改动量相同）。
3. **唯一因记法而异的**是"md→json 解析器"那一步：`:::table` 容器块用
   directive 解析器现成的 API 能直接拿到 `containerDirective` 节点和子节点，
   自己再按行列拆一次；GFM 需要额外接 `remark-gfm` 才有 `table`/`tableRow`/
   `tableCell` 节点（但拿不到 colspan/rowspan，等于白接）；HTML 需要写/接一个
   HTML 表格解析器且要解决"表格内嵌套夹注"的架构冲突（见候选二）。**`:::table`
   在"解析层"这一步成本最低**。

### 三方对照小结

| | GFM 管道表 | HTML `<table>` | **`:::table`（推荐）** |
|---|---|---|---|
| 合并格 | ✗ 表不出 | ✓ 原生 | ✓ `{n}` 跨列＋`^n`/`^` 跨行，均已验证（漢書/卷013、遼史/卷66） |
| 格内夹注等行内记号 | ✓ | **✗ 落入不生效区，需特例** | ✓ 原生嵌套 |
| 复用现成解析器 | 需另接 remark-gfm | 需开 `allowDangerousHtml`＋消毒 | ✓ directive 解析器已在用 |
| 与现有 `:::tt` 容器同构，好维护 | ✗ | ✗ | ✓ |
| 网站解析层改动 | 小（但拿不到合并信息，白做） | 中（HTML 解析＋夹注特例） | 小 |
| 网站渲染层改动 | 三者相同（结构化 JSON → `<GujiTable>`，与记法无关） | 同左 | 同左 |
| 人工写/校对友好度 | 高（业界通用） | 低（标签易错，晉書/宋書已踩过 `<td>` 不闭合的坑） | 中（`{n}`/`_` 需要学，但贴近现有"一行一格"习惯） |

**推荐 `:::table`。**

## 三、转换原型

`古籍文本/scripts/table_convert.py`：

- `refetch <page_title>`：联网重抓维基原始 wikitext/HTML（复用
  `scripts/fetch-book-fulltext/wiki_api.py` 的 `get_revision()`，自带 3 秒节流
  与磁盘缓存），解析出真实表头／colspan／rowspan／空格，转换成 `:::table` 记法，
  同时产出一份浏览器可看的 HTML 预览（真 `<table>`，colspan/rowspan 原生展开，
  夹注渲染成小字 span）。这是**推荐路径**——只有回到源头才能补回 §一 发现丢失
  的信息。单元格内容清洗复用 `guji_clean.wikitext_to_guji_markdown()`（同一套
  模板/夹注/繁简处理，不重新发明）。
- `from-stored <md路径>`：不联网，只吃 book-text 现存的 `<!-- table -->` 文本，
  按表头列数在行尾补 `_` 占位，并把"补了多少处"计数上报——**降级必须可数**，
  借用 guji-markdown spec §0.5 的同一条原则，不假装能复原丢失的信息。
- `demo`：一次跑通方案挑的 6 个样例，产出到 `展示样张/表格/`。

**6 个样例**（覆盖 §一·2 实测出的形态谱系，见 [展示样张/表格/index.html](展示样张/表格/index.html)）：

1. 宋史/卷210 宰輔年表——纯矩阵＋空单元格丢失范例
2. 漢書/卷013 異姓諸侯王表——两层表头＋表头行真实 colspan＋夹注，最复杂的一例
3. 新唐書/卷073上 宰相世系表——稀疏矩阵，14 个子表，验证"一章多表"场景
4. 元史/卷096 食貨志官俸表——小表，验证"首格为空"这种最容易错位的情况
5. 遼史/卷66 皇族表——**数据行**真实 rowspan＋colspan 密集出现，验证 `^`／`^n` 续格标记（§一·3 全量扫描定位到的 24 个真合并格样本之一）
6. 遼史/卷42 曆象志損益表——裸 HTML `<table>` 写法，验证 wikitext 与 HTML 两条解析路径

全部 6 例都是**真实重抓、真实解析**，不是手造数据；HTML 预览可以直接在浏览器
打开看到合并格与夹注的渲染效果（浏览器原生按 `rowspan`/`colspan` 属性展开，
不需要额外代码）。

**已知局限**（如实交底，不夸大原型完成度）：

- 解析器覆盖了本方案样例遇到的 wikitable/HTML 写法，**没有做成能应对任意生僻
  维基表格模板的通用 CLI**——例如极少数用 `{{Sfootnote}}` 等罕见模板做表内引用
  的写法，没有专门测试过；全量重抓时是否会撞上目前 6 个样例没覆盖的写法，
  没有逐一人工核对全部 129 章的转换结果（只核对了 6 个样例＋抽查了 §一·3
  统计脚本的中间结果）。
- 本文档更早一版曾写"数据行没找到真 rowspan，暂不实现续格标记"——那是只
  凭 6 个样例下的结论，**已被 §一·3 的全量重抓推翻并改正**：`^`／`^n` 续格
  标记现在已经实现（`render_notation()`），且用遼史/卷66 这个真实密集样本
  验证过（HTML 预览里能看到浏览器原生展开的 `rowspan`/`colspan` 单元格）。

## 四、维基原页的合并格信息：怎么补回来

任务书问："是从 dump 重抽（给出命令和耗时），还是接受「合并格丢失」"。

**本道实测结论：不需要 dump，直接用 API 逐页重抓即可**——129 章规模小，
`scripts/fetch-book-fulltext/wiki_api.py` 的 `get_revision(page_title)` 已经是
现成、经过验证的封装（`action=query&prop=revisions&rvprop=content`），自带
**3 秒／次节流＋磁盘缓存**（`.wiki_cache/`，重跑不重复打网络）。本道在云端会话
环境（无 dump、无 guji-sources，见任务书模板 §二"云端拿得到什么"）里直接跑通：

```bash
cd scripts/fetch-book-fulltext
python3 -c "
import wiki_api
r = wiki_api.get_revision('宋史/卷210')
print(r['exists'], len(r['content']))
"
```

**耗时**：本道实测把 129 章全部重抓了一遍（§一·3 的合并格全量统计就是用这次
重抓结果算出来的）——**129 页、0 次失败**，实际耗时约十几分钟量级（含少量因
请求过密触发的退避重试；基础节流是 3 秒／页，129 页理论下限约 6.5 分钟，
实测比下限慢是退避造成的，不是接口不稳定）。**`wiki_api.py` 的磁盘缓存
`scripts/fetch-book-fulltext/.wiki_cache/` 被仓库 `.gitignore` 排除在外**
（本道核实过，不是漏提交），所以这份缓存只活在本道会话容器里，**推 main 之后
不会跟着传下去**——下一道接手正式转换时，第一步仍是重新跑一遍 129 次请求，
但既然本道已经实测过"129 页、0 次失败、十几分钟"，这一步的时间与可靠性
是有把握的，不是未知风险。

**dump 路径**（`scripts/fetch-book-fulltext/dump_reader.py`，7.9GB
`zhwikisource-latest-pages-articles-multistream.xml.bz2`）**不需要为这次任务
搭建**——它的优势是"秒级随机访问、免网络"，适合"二十四史全量重抓/未来还要
反复重跑"这种大规模场景（T13/T9 用过），但**dump 文件本身是本地资源，云端
会话拿不到**（见任务书模板 §二），而 129 页规模的 API 请求本来就不算贵，
没有必要为了这次表格重抓专门去准备/传一份 dump。**建议**：这次表格记法定案后
的全量重抓，直接用 API 路径（`table_convert.py refetch`，可批量跑 129 次），
不必等 dump 环境。

**本道已经把这次全量重抓做完一遍**（不是留给下一道的后续问题）：129 章、0 次
失败，结果就是 §一·3 与 §二 引用的 24 章真合并格、43 章真表头、34 章裸 HTML
这几个数字的来源，`^`／`^n` 续格标记也已经据此实现并验证（§三）。但缓存本身
不随仓库传下去（见上），下一道要用时重新跑一次 `refetch` 即可，耗时与可靠性
已有实测数据兜底。

## 五、与自校文本新格式（每字带坐标）的关系

按 [规划/文本.md](../../../team/文本/目标.md) 与 [T7 展示格式方案](2026-09-展示格式方案.md)
用户 09-26 定案：自校文本是完全独立的新格式（每字带页面坐标），版式还原、
原书分行都建在它上面，**不在 guji-markdown 上硬凑**。本方案的 `:::table` 只服务
**外来文本（维基）现有的 129 个表格章**，自校版表格章出现时是"新格式自己的表格
表达"问题，不是"沿用 `:::table`"或"抛弃 `:::table`"的问题——两套格式本来就
不是同一套渲染路径（T7 已定案），本方案不越界替自校格式做决定，只指出：
**自校格式如果也要处理表格（原书表格卷本来就存在页面坐标，天然比现在的维基
线性化更容易保留合并格——每个字有坐标，"哪几个字占了几行几列"是可以从坐标
群推出来的），这是一个对自校格式设计有利的既有条件，供 CV 总管与文本总管
共商自校格式时参考**，不是本方案要解决的范围。
