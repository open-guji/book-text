# 已发文本修订流程的自动化设计

2026-10-23，A34 起草，待 sheldon 审。接在《已发 1.x 文本修订流程》（`2026-10-已发1x文本修订流程.md`）之后：那篇定了「每改动必有意见、裁决、revise、可追溯」，这篇回答「怎样不靠人一步步点」，并把每类对象存哪、有哪些状态、schema 是什么定下来。

写之前核对过的现状：意见池（cv `opinions/schema.py`、`store.py`）、人裁事件规范 v1、`revise.py`、`webstatus.py`、book-text 的 CHANGES 与 `local_check.py`。标「现有」的是已有，标「新增」的是本设计要加的。

## 一、设计原则

1. **事件溯源**：真相是只追加的日志，状态都从日志推出来，不单独存、不手改。意见池已经这样做（`derive_status`），其余对象照办。
2. **一个控制循环，不是一串脚本**：每个阶段是幂等的「调和器」，输入是日志里某个状态的对象，输出是追加几条日志。可以每晚跑、也可以手动单跑，重复跑不出副作用。
3. **人只站在闸口**：自动化负责搬运和检查，人只在这几处出场：裁决（按策略可免）、合并（按策略可免）、major 升版、冲突格、超规模撤除。其余全自动。
4. **每个闸口的免人条件写成策略文件**，策略本身的改动也是一条事件，谁在什么时候放开了什么，查得到。
5. **自动的步骤出错就停在原状态并报告**，不降级、不跳过。

## 二、状态机

意见（现有 `STATUSES`，新增加粗的）：

```
new ─► triaged ─┬─► auto_accepted ─┐
                ├─► auto_rejected  │
                ├─► to_user ─► accepted／rejected／discussing
                └─► dup／forwarded／superseded
accepted／auto_accepted ─► **ready**（修订单已生成且对现行文本验过）
ready ─► **batched**（进了某个发布批）─► **pr_open** ─► applied ─► **published**（读者已看到「已改」）
applied ─► **reverted**（对应撤销事件已落地）
```

发布批（新增，`release`）：`planned → checked → pr_open → merged → published`，任一步失败 `→ failed`（带原因），撤销走 `reverted`。

算法重跑（新增，`run`）：`started → diffed → opinions_emitted → closed`。

## 三、阶段（调和器）

| # | 调和器 | 输入状态 | 做什么 | 输出 | 人？ | 现状 |
|---|---|---|---|---|---|---|
| S1 | ingest | 网站原件、机器检查 | 三源入池，幂等 | 意见 `new` | 否 | 现有（网站每日 Action） |
| S2 | triage | `new` | 模型判定：类别、置信度、修订草案、对读者的公开理由 | `triaged` 事件，带 route | 否 | 现有 |
| S3 | route | `triaged` | 按策略分流：满足免人条件的直接 `auto_accepted`／`auto_rejected`，其余进待办队列 | `to_user` 或自动裁决事件 | 看策略 | 现有（分流有，策略未配置化） |
| S3h | 人裁 | `to_user` | **一个汇总页**：每条意见一屏（原图块、当前字、提议、模型理由），一键采纳／驳回／讨论；批量按钮 | `decided` 事件 | **是（唯一常规人工）** | 新增（页放控制台或网站管理端） |
| S4 | materialize | `accepted`、`auto_accepted` | 把修订草案对**现行文本**干跑 `apply_one`：核 `from`、格号还在、不撞已有格；通过则落修订单并写 CV 人裁事件（带锚，重切不丢），否则退回 `discussing` 并说明 | `ready`；`cv_written` | 否 | 部分（`revise.plan` 有；写 CV 事件的 `cv_events_todo` 缺消费者） |
| S5 | batch | `ready` | 按册聚批：有 ready 就每晚一批；一批规模超策略阈值则分批 | release `planned` | 否 | 新增 |
| S6 | build | release `planned` | 在临时工作树跑 `revise`，调 `bump_original.py`，跑 `local_check.py`，生成差异摘要和「保护格报告」，开 PR（草稿） | release `checked`／`pr_open` | 否 | 部分（`revise`、`local_check` 有，串起来缺） |
| S7 | merge | `pr_open` | 按策略自动合：patch、≤50 格、检查全过、保护格零冲突、无 major；否则请人 | `merged` | 看策略（初期：是） | 新增 |
| S8 | close | `merged` | 记 `applied`（版本、PR、提交）；写 release 记录与格谱系；`publish-status` 给网站；回读者；记度量 | `applied`、`published` | 否 | 部分（`applied`、`publish-status` 有，串起来缺） |
| S9 | revert | 撤销事件 | 同 S4–S8，修订单是「还原」 | `reverted` | 撤销裁决是人 | 新增（见 GUJI-734） |

算法重跑的入口（新增）：

| # | 步骤 | 做什么 |
|---|---|---|
| R1 | rerun（A30 跑 pipeline） | 产出新产物，登记 `run` 记录 |
| R2 | diff | 新产物对现行 1.x 逐格比，分四类：无变化、新增放行、变化（含冲突）、被保护格（有人裁或手改，默认保留） |
| R3 | emit | 每个新增放行与变化格生成一条机器意见（channel `machine:rerun-<run id>`，schema 现有就支持），从此走 S2–S8，不另开一条路；保护格冲突固定走 `to_user`，**策略不允许自动采纳** |
| R4 | 度量 | 记 run 的差异计数与最后各类的处理结果 |

### 4.1 意见日志新增的 kind

在现有 `LOG_KINDS`（ingested、superseded、dup、forwarded、triaged、decided、applied、replied、cv_written）上增加：

| kind | data 必填 | 改状态 |
|---|---|---|
| `revised` | `revision`（定稿）、`verified_against`（文本版本）、`check`（干跑结果） | → `ready` |
| `batched` | `release` | → `batched` |
| `pr_opened` | `release`、`pr` | → `pr_open` |
| `published` | `status_row_ts` | → `published` |
| `reverted` | `release`、`revoke_event`（撤销事件 id）、`reason` | → `reverted` |
| `policy_applied` | `policy_version`、`rule` | 不改（说明为什么能自动） |

`applied`（现有）的 data 增加 `release`、`commit`；`decided` 的 data 增加 `by`（人或 `policy:<规则名>`），这样自动裁决和人裁在日志里一眼分得开。

### 4.4 格谱系

一行一次格变化，按册文件存；任何一格「为什么这样」就是按 `cell` 查这个文件：

```json
{"cell": "3:1:10", "vol": "002", "release": "rel_96mid1ogzk_002_1.0.3",
 "from_version": "1.0.2", "to_version": "1.0.3",
 "before": null, "after": {"c": "□", "lacuna": true, "guess_c": "一"},
 "opinion": "op_span_29a02d06d6", "event": "evt_…", "why": "图上无字，据文意推测一"}
```

插格会让之后的格号变，谱系同时记 `renumber: {"3:1:10+": "+1"}` 一类的映射（总设计已规划的「旧格号→新格号对照表」），旧意见靠它迁移。

### 4.6 策略

```json
{
  "schema": "guji-policy/0.1", "version": 3, "updated_by": "sheldon", "updated_at": "…",
  "auto_accept": [
    {"name": "A-multi-source", "when": {"class": "A", "cells_max": 3, "sources_agree_min": 2, "confidence_min": 0.95, "touches_human": false}},
    {"name": "algo-new-admit", "when": {"channel": "machine:rerun-*", "kind": "new_admit", "confidence_min": 0.98, "touches_protected": false}}
  ],
  "auto_reject": [{"name": "text-ok-with-evidence", "when": {"verdict": "text_ok", "confidence_min": 0.95}}],
  "never_auto": ["C", "touches_protected", "touches_human", "major"],
  "batch": {"schedule": "daily 04:00 America/Los_Angeles", "max_cells": 50, "split_by": "vol"},
  "auto_merge": {"enabled": false, "when": {"level": "patch", "cells_max": 50, "checks": "pass", "protected_conflicts": 0}},
  "major_requires": "sheldon"
}
```

初始值：`auto_accept`、`auto_reject`、`auto_merge` 全部关（`enabled: false`／空表），逐项放开，每次放开前先看影子运行的统计。

## 五、人机分工与可观测

- **人的日常工作量**：每天看一次汇总页（S3h）处理 `to_user`，其余全自动。保护格冲突、C 类、major、撤销，仍然人定。
- **影子运行**：每个自动规则放开前，先「只记录会怎么做」（写 `policy_applied` 但不执行），攒两周与人裁的一致率，达到阈值再放。
- **报告**：每晚一份摘要推给 sheldon：新增意见数、自动处理数、待你定数、开了几个 PR、合并了几个、有无失败；失败的调和器带原因。
- **度量**（`metrics.jsonl`）：每批、每次重跑各一行；看四项：自动化率（自动处理／总数）、闭环时长（入池到 `published`）、撤销率、重跑后新增放行数／变化数。

## 七、要你定的

1. 调度放哪里：建议用中心库 Worker 令牌跑在云端定时任务（环境变量已有令牌），不占 GitHub Actions 配额；PR 由同一任务开。你定是否改用 Actions。
2. 汇总页放控制台还是网站管理端（建议放控制台，已有裁决台与登录）。
3. 起步策略：全人裁（只自动化 S4–S8），还是一开始就放开「多源一致的 A 类」。我建议前者。
4. 合并自动化（P8）是否要，什么条件。
5. 度量要不要对读者公开（网站显示「本册已迭代 N 轮」之类）。
