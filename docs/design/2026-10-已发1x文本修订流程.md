# 已发 1.x 文本之后怎么改：修订流程

2026-10-23，sheldon 同意按此落地（五项待定事项按各自括号里的建议默认值执行）。写于 A34。依据：M11 总设计（`ai-team domain/网站与运维/` 与 cv `doc/design/M11-网站反馈流程-调研与总设计.md`）、cv `revise.py`、book-text `CLAUDE.md` 与 `docs/design/2026-10-文本版本号与仓库流程.md`。已有的部分标「现有」，要新做的标「待建」。

## 一句话

文件不手改。任何一处改动，不管来自读者、算法还是我们自己看出来的，都先成为意见池里的一条意见，再由人（或经授权的规则）写一条裁决事件，最后只经 `revise` 工具生成新版本；每一步都带理由和证据，合并后可以从文本里的某一格一路倒查到当时的理由，也可以靠一条撤销事件走同样的流程退回去。

## 一、三个来源，一个入口

| 来源 | 怎么进 | 现状 |
|---|---|---|
| 读者反馈 | 网站 → 意见池 | 现有 |
| 算法更新（重跑） | 重跑产物与现行 1.x 逐格比对，每个差异格生成一条「算法建议」意见（source=algo，带算法版本） | 待建（GUJI-718 机器报错入意见池是同一条路） |
| 我们自己看出来的 | 手工新建意见（source=internal，写明谁、在哪看到、截图块） | 待建，入口可先用 `guji opinions` 命令 |

要点：内部发现也必须建意见，不能直接动文件。这样所有改动只有一种形状。

## 二、裁决：事件才算数

1. 意见 → 分类（A 改字、B □↔字、B′ 排除框转格、C 切分变化），写出具体修订：格号、from、to、证据图块。
2. 人写裁决事件（现有人裁事件规范 v1：谁、何时、动作、理由、证据），状态为采纳、驳回或搁置，驳回要写公开理由（会回显给读者）。
3. 算法和读者都只提议，不能代替裁决。可以对低风险的类（比如多源一致的改字）事先写明规则，授权自动采纳；规则本身也是一条要记录的事件（谁授权、范围、有效期）。

## 三、落地：只走 revise，一批一个 PR

1. `guji opinions revise` 读已采纳的意见，改 char/cord，伴生层（标点、实体）跟着改，文本线升 patch，写 `CHANGES.md`，打印 PR 正文。（现有，A／B／B′ 三类；C 类还不做）
2. CHANGES 每行列出意见 id 与事件 id；PR 正文列「格、前、后、类、意见」表（现有）。
3. 校验：`local_check.py` 之外，**新增一条规则（待建）**：char/cord 里任何格的变化，必须能在 CHANGES 的意见 id 里找到对应；对不上就红。这样手改会被卡住。
4. 合并后，意见在池里记 applied（带版本、PR），再 publish-status，网站给读者回显「已改」。
5. 批次规模：沿用现行版本号规则，≤50 处逐处改算 patch，整批规则化改动算 minor，major 仍要你点头。

## 四、事后追查与回退

- **向前追**（这格为什么这样）：文本格 → CHANGES 行 → 意见 id → 裁决事件（谁、为什么、证据图块）→ 原始反馈。再加一张每次修订自动生成的「旧格号→新格号」对照表（总设计已定位置：中心库 `feedback/lists/revisions/`），插格后旧意见迁得过去。
- **回退**（改错了）：不 `git revert` 手改。对原事件写一条「撤销」事件，写明错在哪，再走一遍 revise 生成下一个 patch，CHANGES 引撤销事件。历史不删，只追加。
- **算法更新时的保护**：重跑结果先和现行 1.x 对比，差异分三类：新增（原来不放行、现在放行）、变化（有人裁或手改的格被改）、无变化。**有人裁或手改的格默认保留，冲突的逐格报你**，经你同意才覆盖线上；每轮记录版本和受影响册数作为质量度量。
- **存量**：1.0.x 里没有事件对应的手改格（GUJI-716 盘点过）要逐格补成事件或登记为「人工格」，否则回溯会断在这里。
