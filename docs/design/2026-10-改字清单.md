# 改字清单 NNN.char-edits.json（2026-10，草案）

起因：文本 0.x 精校期间，A32 在 dev 上成批落票改字。标点、实体两层外挂在字的格位上，靠校验字（punct 的 `pre_char`、entity 的 `text`）核对，改一个字就会触发 F-OV-02 硬拦，改字的提交推不上 dev。原来的办法是「推分支，等 A33 重标」，每轮都要等。

这份方案综合了 A33 的初稿和 A34 的意见（2026-10-26）。改字方只登记**改了哪些字**，不分别登记标点、实体各自的待办；标点、实体要怎么调整，都由工具从这份清单推出来。

## 一、适用范围

- 只用于文本线 **0.x**（精校中，`proofing: true`）。文本 1.x 起，改字走修订流程（cv `revise.follow_companions`），伴生层在同一个 PR 里就地跟进。1.x 的册带着清单，按硬错报。
- 只收**单格替换**：格数不变，锚点不动。增删字、整句改动不进清单。这类改动会让后面所有下标整段错位，仍然硬拦，照旧推分支请 A33 重标。

## 二、文件

位置在 `<版本目录>/NNN.char-edits.json`，和 `NNN.char.json` 同目录。它是旁路文件，不在 `index.json` 里声明，网站按 `*_file` 字段读文件，读不到它。清单清空后直接删掉文件，不留空文件。

```json
{
  "schema": "guji-char-edits/0.1",
  "book_id": "96mid1ogzk",
  "volume": 7,
  "base_text_version": "0.3.0",
  "edits": [
    {"anchor": "5:4:8", "old": "□", "new": "確", "base_commit": "e45960c4fb", "ref": "007-r4", "by": "A32"}
  ]
}
```

| 字段 | 说明 |
|---|---|
| `base_text_version` | 清单里第一条改字之前的文本版本。伴生层的 `text_version` 不得低于它，否则说明之前还有没登记的改字。 |
| `anchor` | 格号，同一格只登记一条。同一格多次改字时，`old` 留最早的字，`new` 取最新的字；改回原字就把这条删掉。 |
| `old` / `new` | 改前的字 / 改后的字。 |
| `base_commit` | 改字前的提交号，供复核用。 |
| `ref` | 出处：意见 id、待审单 r 号或 GUJI 卡号。和 `check_cell_provenance` 对照用。 |
| `by` | 改字方。 |

## 三、校验（`original_version.anchor_mismatches` 一处分软硬）

`anchor_mismatches(char, line, data, edits=None, soft=None)`：

1. 校验字对不上时，满足以下全部条件，这条进 `soft`（F-OV-02s，软提示）：
   - 文本线是 0.x；
   - 这一格登记在清单里；
   - 文本现在是 `new`；
   - 校验字仍是 `old`。

   实体条目要求：它覆盖的每一个对不上的格都满足上面的条件，且实体长度不变。
2. 其余情况仍报 F-OV-02 硬错，包括：
   - 锚点不存在（删了字）；
   - 格没登记（插字导致位移，或者漏登）；
   - 文本线已是 1.x。

   这几种情况判断起来不需要读 git。
3. 不传 `edits` 时，行为和原来完全一样。`bump_original.py` 升伴生层时仍然要求零对不上，所以要先 sync 再升版本。

F-OV-15（硬错）检查清单本身：

- `schema`、`book_id`、`volume` 与所在册一致；
- 文本线是 0.x；
- 每条都有 `anchor`、`old`、`new`、`base_commit`；
- 锚点在文本里，且文本现在是 `new`；如果不是，说明清单过期了；
- 伴生层的 `text_version` 不低于 `base_text_version`。

F-OV-15s（软提示）：清单里的格在各伴生层都已经对上，提示可以清掉。

## 四、工具 `scripts/book-text/char_edits.py`

**`record`（改字方用）**

```
char_edits.py record <版本目录> --chapter NNN --old-char git:<改字前提交> --ref 007-r4 --by A32
```

比对新旧两份 char，把改了字的格并进清单；遇到增删字直接拒绝。清单和改字放在同一个提交里一起提交。

**`sync`（A33 用）**

```
char_edits.py sync <版本目录> --chapter NNN [--dry-run]
```

- **做什么**：机械同步。登记格上仍是 `old` 的校验字，改成 `new`：punct 改 `pre_char`，entity 改 `text`。
- **不做什么**：不重新断句，不动 `target`、`source` 或其他字段。人裁、手改的条目也只同步校验字，所以不会冲掉任何人裁结果。
- **输出**：
  - 字变了的专名，需要核对挂法是否还对；
  - 改字所在的句子，由人决定要不要重标。确实要重标的，用 `punct_redo.py plan/apply`。如果句子里有人裁的条目，先单独列出来交 A34 走「会冲掉的人裁手改」摘要。
- **收尾**：同步完的格从清单删掉，清空就删文件。之后用 `bump_original.py` 给有改动的那条线升 patch。

## 五、流程

1. A32 在 dev 上落票改字，`record` 登记清单，`bump_original --line text`，提交、推 dev。这时 F-OV-02 只是软提示，`local_check --dev` 能过。
2. A33 在每日合并（洛杉矶 03:30）之前跑 `sync`，核对字变了的专名、要不要重标，然后升 patch、推 dev。
3. `daily_merge.py` 在 PR 描述里列出仍未清的清单（册、格数）。没清完也可以进 main：单格替换不会让显示错位，网站只是显示旧标点配新字。但 1.x 的册带着清单会被硬拦。
